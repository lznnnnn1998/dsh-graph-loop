## 3. Architecture as actually implemented

- `packages/loop` implements `AgentFactory` (`src/loop/index.ts`); the bundle patch
  disables the stock row and inserts `graph-registry`, `graph-router`,
  `graph-runtime`, `graph-loop`, `graph-tools` (`cordis.patch.yml`).
- `createGraphTurnDriver` (`scheduler.ts:179`) owns one topology per turn. Plans
  the kernel can route (linear, one `callFailed` branch, safe node ids) use
  `KernelTopology` (`kernel/topology.ts`); everything else uses
  `FrontierTopology`. The live driver is re-installed on replans/proposals.
- Model-visible control directives are `user/message` events with source
  `graph-node`; subagent batch summaries now use `subagent-result`; benchmark
  retry corrections use `bench-retry` (`benchGuards` off by default).
- Checkpoints on the live path are `GraphState` snapshots persisted at node
  boundaries into `MemoryCheckpointer`, keyed by `plan.id` (task fingerprint
  hash) + `atSeq`. No durable saver, no reader, no cross-process history.
- `graph-ui` serves the Graph tab (`/graph-chat/api/*`), reading in-memory
  `traceHistory(sessionId)`; optional `traceDir` JSON is best-effort debug
  output, not the checkpoint store.

## 5. Durable checkpoints: feasibility and verdict

### 5.1 Is `@deepseek-ai/dsh-storage-domain` present, and how is it mounted?

Yes. `/Users/zhinan/deepseek-harness/packages/storage/storage-domain`,
version `0.2.1-rc.3` (matches `engines.dsh`), peers `@deepseek-ai/dsh-storage`
and `@deepseek-ai/cordis`, deps `@deepseek-ai/schemastery` + `zod@4.4.3`
(the repo already links the host `zod`; no version gap). Public API
(`src/index.ts`, `src/domain.ts`, `src/spec.ts`):

- plugin name `storage-domain`, `inject = ['storage']`, `Config =
  { backend: string, routes?: Record<domain, backend> }`; provides
  `ctx.storageDomain: DomainFacility`;
- `DomainFacility.open(spec): Promise<Domain<S>>`, `get(name)`, `closeAll()`;
- `defineDomain({ name, version, layout: 'single'|'per-record',
  invalidRecords: 'backup-and-skip'?, global?, tables })`, `domainTable(zod)`;
- `Domain.table(name)` → `KvTable` with **synchronous** `get/entries/keys/size`
  and **async** `put/delete/deleteMany/update`; `Domain.close()` is
  caller-owned (idiomatic `ctx.effect` disposer);
- record schemas are zod; names must match
  `UNIT_NAME_RE = /^[a-z][a-z0-9_]*$/` — **hyphens are invalid**, so the
  cycle-3 design name `'graph-loop'` would throw at module load; use
  `graph_loop` (tables: `checkpoints`).

Mounting: the host profile supplies the service; the plugin only needs the
optional peer and to open its own domain. Precedent: `packages/schedule/schedule`
uses `static inject = [..., 'storageDomain']` and `ctx.storageDomain.open(...)`
in `[Service.init]`; `packages/workspace/workspace` does the same. For this
plugin the inject should stay **optional** (`ctx.inject(['storageDomain'], …)`
inside the service lifecycle, with `MemoryCheckpointer` as the documented
fallback) because a custom minimal profile may omit base storage; a hard
`static inject` would make the loop unbootable there. `scripts/link-dsh.sh`
must also link the package for typecheck (it currently links neither
`dsh-storage` nor `dsh-storage-domain`), and `package.json` needs
`@deepseek-ai/dsh-storage-domain` (+ `zod`) as optional peers.

### 5.2 Is there a clean injection point for a `PlanCheckpointer` / thread id?

**Yes for the saver, no for the thread id today.**

- `KernelTopologyOptions` (`topology.ts:40-44`) has `kind/taskHash/maxSteps`
  only; the `KernelDeps` it builds (`topology.ts:72-86`) omits `checkpointer`,
  so `resolveKernelDeps()` falls back to `MemoryCheckpointer`
  (`plan.ts:184`). Passing an optional `checkpointer` through those two spots is
  a ~5-line change and covers **every live node boundary** (see §2 correction).
- The checkpoint key today is `plan.id` (`persist`, `plan.ts:509`), which is the
  task fingerprint hash (`scheduler.ts:247` passes `taskHash: next.id`), not a
  per-session/turn identity. Two sessions with the same task text would share a
  durable thread. The live turn does know the identity: `ReactLoopAgent.id`
  (session id) and the turn number `const turn = phase.turn + 1`
  (`agent.ts:514`), immediately before `beginTurn(...)` (`agent.ts:534`).
  `TurnTask` (`scheduler.ts:30-40`) and `GraphTurnDriverOptions` have no
  `threadId`; `KernelDeps.runContext.turn` exists (`plan.ts:118`) but
  `KernelTopology` does not pass it and `persist()` ignores it. The clean route
  is `TurnTask.threadId = `${this.id}:${turn}`` → driver closure →
  `KernelTopologyOptions.threadId` → `KernelDeps.threadId`, and
  `persist()` uses `deps.threadId ?? plan.id` (keep the fallback for
  `graph_run`/tests). `install()` is re-called on replans, so the thread must
  live in the driver closure, not in the topology instance.

### 5.3 What would persist, what stays session-log-authoritative, restart/resume?

- **Persist:** `GraphState` at node boundaries (journal, `superstep`, `next`,
  `status`, `facts`, `artifacts`, `children`, `budget`, `replans`), keyed
  `threadId:seq` (zero-padded seq for range scans), `layout: 'per-record'`,
  `invalidRecords: 'backup-and-skip'` — derived, disposable data. Do **not**
  persist conversation messages or tool results: the session log remains the
  authoritative record (`MERGE-LANGGRAPH.md` C5/D10; docs already say this).
- **Restart:** stock DSH resume appends synthetic closers to an interrupted
  final turn (`interruptedTurnClosers`, `packages/core/agent-loop/src/index.ts:795-805`:
  missing tool errors, `step/end`, `turn/end`) and then starts a **new** turn
  on the next request. A checkpoint for the closed turn is therefore orphaned;
  the next turn gets a new turn id. Cross-process mid-turn resume is the product
  decision D10 and is deliberately out of scope. Even if D10 were reopened,
  resuming from the last node boundary means re-running the in-flight node,
  whose tool side effects are already in the session log — duplicate-effect
  safety would need its own design. This is not a checkpoint bug; it is the
  reason a saver alone is not a resume feature.

### 5.4 Why an implementation now would be half-implementation

1. **No reader.** `PlanCheckpointer.load(` has zero call sites in
   `packages/loop/src`; `getState`/`getStateHistory` (`langgraph.ts:388-412`)
   belong to a separate native `CheckpointSaver` path (`CompiledGraph` API used
   by `graph_run`/tests), not to `KernelTopology`. A durable `put` without a
   consumer is write-only code.
2. **The only non-D10 consumer is the Graph tab replay/time-travel** (M3:
   expose `getState`/history "for replay and time travel"). That needs a new
   read API in `graph-ui` plus a client view for node-level checkpoints; the tab
   today renders per-turn `GraphTurnSnapshot`s from `runtime.traceHistory`, a
   different shape. This is a designed feature, not a 2-hour audit patch.
3. **Failure policy is undesigned.** `persist()` is awaited inside node
   execution; a storage backend error would propagate through `advance()` and
   fail the turn. Derived-data writes must be fail-open (log and continue,
   respecting `DomainError('unknown-state')` quarantine), and the store needs a
   retention policy; neither exists yet.

### 5.5 Verdict

**Defer. Explicitly do not half-implement a durable saver this cycle.**
The blocker is not infrastructure — storage-domain is present in shipped
profiles and the live kernel already checkpoints at node boundaries — it is
product/consumer scope: there is no resume path without reopening D10, and the
only legal consumer (Graph-tab replay/time travel) is a new UI/API feature.

When the product owner approves replay/time travel, the smallest complete slice
is (one change, all-or-nothing):

- new `packages/loop/src/persistence/domain.ts` (`graph_loop`, `checkpoints`,
  zod record, per-record, backup-and-skip) and
  `packages/loop/src/persistence/storage-checkpointer.ts`
  (`PlanCheckpointer` + `history(threadId)` over `KvTable`);
- `plan.ts`: `threadId` on `KernelDeps`/`ResolvedKernelDeps`, `persist()` uses
  it; `topology.ts`: `checkpointer`/`threadId` in options, into deps;
  `scheduler.ts`: `TurnTask.threadId`, driver option, pass through `install()`;
  `agent.ts`: `${this.id}:${turn}`; `loop/index.ts`: open the domain behind an
  **optional** `ctx.inject(['storageDomain'])`, close via `ctx.effect`
  (`Domain.close()`), fall back to `MemoryCheckpointer`;
- `graph-ui/src/graph-chat.ts` + `client/graph-view.js`: a read-only history
  route and view (thread → seq list → state), no resume action;
- tests: fake `KvTable` round-trip/order/isolation; `KernelTopology` two-node
  run writes one row per boundary under the supplied thread id; a **new**
  topology reconstructs `current()`/`state` from `load(thread, seq)`; a write
  failure does not fail the turn; history order/retention; packaging
  (`link-dsh.sh`, optional peer, build:check);
- docs: `STATUS.md` gap 2/M3, `MERGE-LANGGRAPH.md` §3.3, `README.md`
  limitation; keep "no cross-process resume (D10)".
- Correct the cycle-3 design name to `graph_loop`; keep the session log
  authoritative and never replay checkpoints into the prompt.

## 10. Verdict on architecture B

Architecture B remains what is actually implemented and documented: the
dedicated plugin replaces the stock loop via `AgentFactory`, the kernel owns
control flow for the shapes it can route, and the frontier owns the rest.
Durable checkpoints are the one architecture item still missing; this cycle's
task was to decide whether they can be implemented safely now. They cannot —
not for infrastructure reasons (those are ready), but because the product
consumer is absent and the one legal consumer is a new UI feature. Keep B, keep
the in-memory checkpoint claim, and defer the storage slice to a cycle that
also ships replay/time-travel.
