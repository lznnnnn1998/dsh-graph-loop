## 2. Current architecture as actually implemented

**Install/replacement.** `packages/loop/cordis.patch.yml` disables the `agent-loop` row and inserts
five graph rows; `packages/graph-ui/cordis.patch.yml` inserts `graph-ui`; `packages/mode` inserts
the Explore preset. Because `setFactory` is exclusive, exactly one loop registers. This is B, done
at the profile/bundle layer plus the `AgentFactory` seam (not by editing DSH).

**Turn/step path.**

1. `ReactLoopAgent.beginTurn` (fork, `packages/loop/src/loop/agent.ts:503-511`) calls
   `graphDriver.beginTurn({text: <pending user text>, surface:'api'})`.
2. `beginTurn` (`scheduler.ts:337-444`) fingerprints the task and installs one plan:
   - `forceFallback` (subagent child, depth > 0) or trivial text → single-node `fallbackPlan`;
   - `mode: 'propose'` → bootstrap frame, model authors a plan via `graph_plan`;
   - default `dynamic` + `composition: true` → `selectEnvelopeForTask` (`scheduler.ts:390`) +
     `synthesizeComposition` (`:397`) → linear stage chain;
   - fallback `dynamic` → legacy `synthesizeTopology`;
   - `template` → curated library.
3. `install` (`scheduler.ts:238-253`) picks `KernelTopology` (LangGraph or Minimal) when
   `canKernelDrive(plan)`, else `FrontierTopology`.
4. Each DSH step injects one node directive as a user message (`agent.ts:419-437`), narrows the
   admitted tools to the plan universe (`agent.ts:434-480`, `step-tools.restrictToolSet`), runs the
   stock step, then reports the outcome to the graph (`agent.ts:655-665`).
5. Node failure starts a bounded boundary replan (recovery or verify-repair graph,
   `scheduler.ts:271-298`), max 1–2 replans per turn from the plan budget.
6. Subagent nodes are batched and run as real child activations (`agent.ts:224-268`); children are
   forced to the single-node fallback (`scheduler.ts:372-377`).
7. `graphRuntime` (`packages/loop/src/runtime.ts`) keeps proposals, live snapshots, turn traces in
   process memory, optionally writing JSON trace files when `traceDir` is set. The Graph tab and
   `/graph-chat` read that service (SSE), not the session log.

**Kernel.** `KernelTopology` compiles the plan and pauses before each node; the DSH step is the node
body; `advance()` feeds the step outcome back as a bridge executor, then the kernel routes/checkpoints
and pauses again. This is a genuine kernel round-trip, but only for linear, `always`-edge, no-subagent
plans. Everything else — the only place "arbitrary graph" exists — is `FrontierTopology`.

## 3. Drift from intent

**D1 — Architecture narrative flipped in docs while code stayed B.** `docs/COMPOSITION.md:58,86`
("Control plane over the stock loop first", D12) and `:454-463` ("reconsider the fork only if 2+
triggers fire") present the control plane as the active direction and supersede the loop-first plan.
`README.md:6-7,58,68` repeats "the long-term path is a control plane over the stock loop".
`PROGRESS.md` "Direction reset" does the same. The code is still the fork (B). Per the lead decision,
the docs are the drift: demote them to history and make one normative statement match B.

**D2 — Benchmark expansion consumed the cycle and is not product evidence.** Commits
`6b99b83 → c384bb8` added Docker/Harbor, a Terminal-Bench adapter, a 7-task subset, a smoke task, a
retry-cap policy, and a suite switch (OfficeBench deleted, local 20 archived). None of it exercises a
graph capability. The result is `0.0` on clean trials (`bench/official/results/README.md`), and the
only favorable numbers come from a dirty-worktree run whose manifest now says it "must not be cited
as commit-bound evidence". `README.md`/`docs/PRODUCT-LINE.md` still headline the −50% prompt number.

**D3 — Benchmark heuristics were patched into the generic loop.** `agent.ts:570` scans assistant
content for `"DSML"`; `:610-628` retries a node up to 1 extra step for printed tool syntax;
`:629-641` retries any "mutating" node that did not mutate; `step-tools.ts:6-18` hardcodes DSH tool
names (`write`, `edit`, `bash`, `pwsh`, `sed -i`, …) and shell-mutation regexes. These are
task-suite-specific enforcement, not graph-loop features, and they contradict the repo's own
"tool-agnostic, no hardcoded product/tool names" rule (`packages/core/src/compose.ts:1-20`).

**D4 — Config knobs exist only for benchmark harnesses.** `toolPolicy: 'preset'` and
`composition: false` (`packages/loop/src/loop/index.ts:266-285`, `scheduler.ts:388`) are documented
as "needed by benchmark harnesses" and "needed by harnesses that exercise legacy topologies". They
keep a second, un-defaulted execution path alive and are the main reason the old topology code cannot
be deleted.

**D5 — Mode/teams scope creep.** `packages/mode` (Explore preset) is a delivery vehicle, fine, but
`packages/mode/src/reuse.ts` (303 lines) + `mode-reuse.test.ts` (16 of 168 tests) implement teammate
reuse/duplicate-spawn policy with no connection to graph execution. That is separate product scope
riding the same package.

## 6. What blocks "complete"

1. **Kernel coverage is inverted relative to the value claim.** The only graph features LangGraph
   would uniquely provide (branching, conditional edges, Send/fan-out, durable checkpoints) are
   exactly what `canKernelDrive` routes away from LangGraph (`kernel/topology.ts:238-262`). The
   default live path is linear, so LangGraph currently adds adapter risk without unique capability.
2. **Checkpoint durability does not exist in the live path.** `MemoryCheckpointer` per process
   (`plan.ts:154`), LangGraph compiled without a saver (`langgraph.ts:266`), graph runtime state in
   Maps (`runtime.ts:54-57`), no session-log graph state, no resume. A restart loses the turn's graph
   position; `checkpoint.ts` is an unused contract.
3. **Real graph execution (parallel branches, cycles, failure routing) only runs on
   `FrontierTopology`**, which is bespoke code, not the LangGraph kernel the intent asked for. To
   "complete" B honestly, either LangGraph must own those plans or the intent claim must be restated
   as "graph scheduler + optional LangGraph routing".
4. **No reproducible product evidence.** Active suite defined-but-unrun; archived favorable run is
   explicitly non-reproducible; official clean trials are 0.0. There is no offline/mock A/B that a
   reviewer can rerun and trust.
5. **Release/maintenance hygiene.** `build:check` red, no CI, no fork-sync check, numeric
   `FiberState` coupling, benchmark heuristics hardcoded in the generic loop.
6. **Docs disagree with code and with the lead decision** (control-plane narrative vs the fork).
   That is a completion blocker because "complete" is judged against the stated architecture.
