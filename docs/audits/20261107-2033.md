## 3. Architecture as actually implemented

- **Seam:** `AgentLoop` publishes itself through `ctx.agents.setFactory()`; the install patch
  disables the stock `agent-loop` row and inserts `graph-registry`, `graph-router`, `graph-runtime`,
  `graph-loop` and `graph-tools` (`packages/loop/cordis.patch.yml`). One loop per profile is
  enforced by DSH's exclusive factory.
- **Fork surface (bounded):** 8 files in `packages/loop/src/loop`; `agent.ts +341/−15`,
  `index.ts +147/−10`, `graph-node.ts` and `step-tools.ts` local-only, and `assistant-stream.ts`
  identical / `constants.ts`, `inbox.ts`, `runtime-context.ts` `@module`-header-only. This matches
  the script's expectation; the patch is large but concentrated in the loop files.
- **Turn = one plan:** the scheduler fingerprints the task and installs a composed plan
  (`synthesizeComposition`, default `composition: true`) or the legacy `synthesizeTopology` /
  template / fallback paths; every DSH step is one graph node and the kernel pauses before the next
  node (`KernelTopology`).
- **Kernel:** `createKernel()` defaults to LangGraph, `MinimalKernel` fallback when the optional
  dependency is absent. `canKernelDrive()` owns only linear plans and one `callFailed` failure
  branch, with one unconditional control out-edge per node, valid node ids and no frontier-only
  conditions. Everything else stays on `FrontierTopology` (documented).
- **Checkpoints/trail:** written at node boundaries through `PlanCheckpointer`; default
  `MemoryCheckpointer` is process-local. `GraphRuntime` keeps proposals, run records and turn traces
  in `Map`s, with an optional `traceDir` JSON dump for the preview panel (`runtime.ts:53-129`).
  There is no `getState`/history API and no restart resume; the session log remains authoritative.
- **UI:** Graph tab + `/graph-chat` read the live `GraphRuntime`; installed e2e passes.
- **Evidence:** product20 defined/unrun; one member 0.0/0.0 standalone trial; stress line 0.0; no
  benchmark suite was added or expanded in the last two commits (`git log -- bench` ends at
  `aecc0f3`).

### P1-1 — Graph subagent batch results still claim the human `user` source (new, top P1)

`ReactLoopAgent.runSubagentBatch()` injects every child summary as
`createUserMessage({ ..., source: { kind: 'user' } })` (`packages/loop/src/loop/agent.ts:263-269`).
The injected message goes through the inbox decision and is persisted as `user/message` with that
source. I reproduced the consequence with the repo's own subagent e2e (mock LLM, dev overlay):

```
PASS e2e parallel subagent nodes  (home /tmp/dsh-audit-sub.ANV0qw)
subagent_messages=2  kinds=[{d_search: user}, {d_fetch: user}]
human_source_messages=3
last_human_text="[subagent d_fetch] (completed) child ok"
```

So after a subagent turn the stock `latestUserQuestion` filter (and DSH UI's human-bubble/steering
classification) reads a **synthetic child summary** as the latest human message. This is the same
class of defect cycle 2 fixed for node directives, on the loop's advertised “parallel subagent
nodes” feature. It is not P0 *today* because the default installed path (`composition: true`)
composes step-only plans, so subagent nodes only appear on the dev overlay / legacy
`synthesizeTopology` fallback; the moment subagent plans are enabled by default this becomes P0.

Scoped fix: give the batch result a fork-owned source kind (e.g. `graph-subagent` with `nodeId`;
do **not** reuse the human `user` kind; a DSH `subagent-settled`-style notice is an alternative but
it is defined for a one-line manager account, not a full child output). Add a unit test that no
injected subagent result has `source.kind === 'user'` and extend `scripts/e2e-subagents.sh` to
assert the persisted source kinds and that the human question remains the last human-source message.

### P1-2 — Durable checkpoints and node-trail resume (largest architecture completion item)

`MemoryCheckpointer` is the live saver; `persist()` is correctly called at every node boundary by
both kernels, but LangGraph is compiled with no checkpointer and `storageDomain` is not wired. The
node trail is in-memory in `GraphRuntime` (+ optional `traceDir` dump), so a restart loses graph
state and history; `docs/MERGE-LANGGRAPH.md:89-98,166` (M3) and `STATUS.md:57-58` disclose this.
Scoped next step: implement a `storageDomain`-backed `PlanCheckpointer` (or a LangGraph
`BaseCheckpointSaver`) with `thread_id = sessionId + turnId`, node-boundary writes, `__pregel_*`
stripping and the existing JSON guard; expose `getState`/history to the Graph tab; add a
restart/resume unit test with a fake storage domain. Keep the session log authoritative; do not add
a second conversation log. Cross-process mid-turn resume stays a product decision (D10) — the
minimum deliverable is durable state + replayable history.

### P1-3 (deliberately not implemented) — durable checkpoints: feasibility + concrete design

The code is unchanged; no durability is claimed. A tested in-process saver would be
durability theater because the live turn never passes a `PlanCheckpointer`, and the DSH storage
service is not mounted in this plugin's profiles. The evidence:

- The live turn stepper is `KernelTopology` (`packages/loop/src/kernel/topology.ts:46-56,74-90`). It
  builds `KernelDeps` **without** a `checkpointer`, so `resolveKernelDeps()` falls back to
  `MemoryCheckpointer` (`packages/loop/src/kernel/plan.ts:103-106,154-184,186-205`). `persist()` is
  only called by the LangGraph/Minimal adapters during `runPlan()`
  (`packages/loop/src/kernel/langgraph.ts:789`, `packages/loop/src/kernel/minimal.ts:631`), i.e. the
  `graph_run` tool and tests — not the DSH step loop.
- The live turn's state lives only in `KernelTopology` (`state`, `currentId`, `pending`) plus the
  `GraphTurnDriver` plan/trail (`packages/loop/src/scheduler.ts:179-...`). LangGraph is compiled with
  no saver (`packages/loop/src/kernel/langgraph.ts:264-266`); the adapter-local `getState` /
  `getStateHistory` (`:388-412`) are not a `BaseCheckpointSaver` and are not exposed by
  `KernelTopology`, so the Graph tab cannot replay history today.
- `storageDomain` is the DSH storage-domain plugin (`@deepseek-ai/dsh-storage-domain`, plugin name
  `storage-domain`, injects `storage`). It is **not mounted** for this package: no storage row in
  `packages/loop/cordis.patch.yml`, no `@deepseek-ai/dsh-storage-domain` /
  `@deepseek-ai/dsh-storage` peer dependency in `packages/loop/package.json`, and the linked
  `node_modules/@deepseek-ai` tree contains no storage packages. Wiring it changes the installed
  profile surface and needs a backend route (`ctx.storageDomain.open(spec)`), not just plugin code.
  Its public API is otherwise suitable: `defineDomain` / `domainTable` (zod record schemas, `zod@4.4.3`
  in the linked tree), `Domain.table(name)` → `KvTable.put/get/entries/delete`, `Domain.close()`.

Concrete design for the next cycle (exact files/interfaces):

1. `packages/loop/src/persistence/domain.ts` (new) — `GRAPH_LOOP_DOMAIN = defineDomain({ name:
   'graph-loop', version: 1, layout: 'per-record', invalidRecords: 'backup-and-skip', tables: {
   checkpoints: domainTable<CheckpointKey, StoredCheckpoint>(z.object({...})) } })`.
   `StoredCheckpoint = { threadId: string; seq: number; planId: string; superstep: number;
   nodeId?: string; status: 'running'|'done'|'failed'; state: unknown; createdAt: string }`;
   key `${threadId}:${seq.toString().padStart(12, '0')}` so history is a key-range scan.
   `layout: 'per-record'` keeps each node boundary its own document; `invalidRecords` is right
   because the session log stays authoritative (derived data).
2. `packages/loop/src/persistence/storage-checkpointer.ts` (new) —
   `class StorageCheckpointer implements PlanCheckpointer { constructor(table: KvTable<...>, now?:
   () => string); load(sessionId, atSeq); put(sessionId, atSeq, state); latest(threadId);
   history(threadId): Promise<StoredCheckpoint[]> }`. `put` keeps the existing JSON guard (the
   caller `persist()` already calls `assertJson`), stores `state` only, and does not copy
   `__pregel_*` (this repo's LangGraph root has no native checkpoints).
3. `packages/loop/src/kernel/topology.ts` — add `checkpointer?: PlanCheckpointer` and
   `threadId?: string` to `KernelTopologyOptions`; pass them into `KernelDeps` (line 74) /
   `ResolvedKernelDeps`. `persist()` must key by that thread id (session + turn), with `plan.id` as
   the test fallback.
4. `packages/loop/src/scheduler.ts` — `GraphTurnDriverOptions.checkpointer?: PlanCheckpointer`,
   `TurnTask.threadId?: string` (or `turn`), passed through `install()` to `KernelTopology`. This is
   the only live-path checkpoint write; do not double-write per step.
5. `packages/loop/src/loop/index.ts` — `static inject` += `'storageDomain'` (or `ctx.get` optional
   path), open the domain in `[Service.init]` with `ctx.effect(() => () => domain.close())`, and pass
   `checkpointer` + `threadId = id + ':' + turn` into `createGraphTurnDriver` at `:694`.
6. `packages/loop/package.json` — add `@deepseek-ai/dsh-storage-domain` (and `zod` for the record
   schemas) as peers/optional peers; `packages/loop/cordis.patch.yml` — add `storage` +
   `storage-domain` rows with a backend route, or document that the host profile provides them and
   keep `MemoryCheckpointer` only as the explicit fallback.
7. Tests — `test/unit/kernel-storage-checkpointer.test.ts` with a Map-backed fake `KvTable`

   `test/unit/kernel-topology.test.ts` with a fake storage checkpointer so a two-node run writes one
