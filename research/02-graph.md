# 02 — Graph model, scheduling, matching, replan and checkpoints

> Scope update applied: the `explore` loop **replaces** the stock driver rather than
> wrapping it. This note designs the graph-native loop (turn = one graph run, node = one
> DSH step), the two node executors, the registry graph and task match, replan, durable
> state, and the conformance surface. Every DSH claim cites the checkout; everything I
> could not verify is marked **ESTIMATE** or **OPEN**.
>
> Artifacts: `design/graph-schema.ts`, `design/runtime.ts` (consumes `design/kernel.ts`),
> `design/matching.ts`, `design/replan.ts`, `design/conformance.ts`,
> `design/example-graph.yaml`, `design/measurements.md`.

---

## 0. Verdict in one page

1. **A graph-native driver is buildable as a profile patch, not a source change.** The
   stock loop is a plugin row (`packages/bundle/base/cordis.patch.yml:513-514`) behind a
   public factory slot (`packages/core/agent/src/index.ts:383`). An out-of-tree bundle
   disables that row and registers its own `AgentFactory`; no DSH file changes.
2. **The graph owns step selection, not request construction.** The driver reuses the
   per-step pipeline order (`resolve -> assemble -> agent/pre-step -> step/start ->
   prepareCall -> header -> stream -> tools -> step/end`, `packages/core/agent-loop/src/agent.ts:278-296`).
   That is what keeps compaction, plan-mode, approvals, inbox, persistence and the UI
   working. Re-implementing request construction is the failure mode.
3. **One turn is one run; one node is one step.** The mapping in
   `design/runtime.ts#SUPERSTEP_MAPPING` is normative and becomes the conformance test.
   Parallel nodes are child subagent activations, never concurrent steps in one session.
4. **State is JSON-only and not the source of truth.** The kernel contract already says
   this (`design/kernel.ts` C1/C3/C5): a checkpoint is a runtime facility, the session
   log is the only history, and DSH closes interrupted turns on restore, so there is no
   cross-process mid-turn resume to design for.
5. **Similarity is layered, not cosine.** Artifact pre/post conditions + schema overlap
   + mined co-occurrence (NPMI) + measured success/cost, with embeddings only as a
   tiebreaker. The matcher is a deterministic function of
   `(fingerprint, graphDigest, weightsVersion, presetId)` and runs **once per task**,
   before tool resolution of the first step.
6. **Dynamic node add/remove is recompilation, not mutation.** LangGraph compiles
   topology; replan mutates the plan document, recompiles via `kernel.withTopology`, and
   resumes from the node boundary with `updateState`.
7. **The token win is not per-node schema gating** — measured below: with DeepSeek-like
   cache pricing, per-turn hard gating breaks even only around **120 steps**. The win
   comes from a stable, smaller per-plan tool universe applied at cold points, plus fresh
   subagent contexts for discovery-heavy work.

## 1. Three layers and where the "compute once" step sits

```
INIT (plugin activation, once per process)
  └─ registry graph snapshot  ── live updates: tools/change, system-prompt/change,
     (capability universe)       skills/change, preset revisions, HMR plugin rows
                                    │
REQUEST (once per task / turn)       ▼
  └─ task fingerprint → match → plan document (template instance)
     deterministic, cached on (hash, graphDigest, weights, preset)
                                    │
RUN (per turn)                       ▼
  └─ kernel compile(plan) → supersteps
       superstep = one DSH step (or one parallel subagent superstep)
       node boundary = step/end or injected result → checkpoint
```

**What is knowable at init vs only at request time** (this is where "build a graph at
initialization" breaks if taken literally):

| Fact | When knowable | Source / evidence |
|---|---|---|
| Tool names, descriptions, parameter schemas | init (and later) | `ctx.tools.schemas()`; `docs/tool-catalog.md` is generated by booting plugins |
| Conditional tools (`register(def,{when})`) | per step | `packages/core/tools/README.md#conditional-tools` |
| MCP tools | after server connects | `packages/mcp/mcp-client/README.md` — "after the harness starts" |
| Skills catalog | init + `skills/change` | `packages/skill/skill/README.md#what-the-registry-gives-you` |
| Subagent providers, preset definitions | init | `ctx.subagents`, `agent-preset-registry` |
| Per-agent restrictions (`restrict`) | request time, per agent | `ctx.tools.restrict` |
| Working directory facts | per session | `ctx.workingDirectory`; `working-directory/change` |
| Model route availability | per request | `prepareCall` / `ctx.llm` |
| Tool cost/failure priors | offline, recomputed | `ctx.sessionQuery` + token meter |

Consequence: the registry graph is a **live snapshot with a digest**, rebuilt
incrementally (debounced ~50 ms) and versioned. A match made against digest `D` is never
reused against `D'`. The registry itself is not on the request hot path: the driver holds
one immutable snapshot per process revision.

**Where "compute once" sits precisely.** The task text first becomes visible at inbox
insertion (`agent/inbox/inserted`) or, for a cold start, as the created session's first
prompt. The match runs there — *before* the turn opens — because the first step's tool
set must be resolved before `agent/pre-step` can see it
(`agent.ts:280-290`: claim → `tools.resolve` → `assemble` → `agent/pre-step`). The match is
synchronous CPU work (fingerprint + bounded beam search, sub-millisecond), so it is safe
at that point; optional heavier signals (co-occurrence refresh, embeddings) are computed
offline or before the turn and passed in as versioned data. Inside one run the plan is
fixed; only a replan re-enters the matcher (to re-instantiate a mutated template or fall
back).

## 2. Scheduling: turn → one graph run, node → one DSH step

### 2.1 The mapping table (normative)

| Graph concept | DSH durable fact(s) | Notes |
|---|---|---|
| run start (`invoke`) | `turn/start`, then `step/start` for superstep 0 | the turn is opened by the driver, then the first step |
| superstep, node executor `step` | `step/start` → `request/header` → `system/message`? → `user/message` → `assistant/message` → `tool/call`* → `tool/result`* → `step/end` | exactly the stock step shape |
| superstep, node executor `subagent` | same open step, no model request: synthetic `tool/call(name="graph:delegate")` per branch + `subagent/catalog` + `tool/result(structured)` | children run concurrently; step/end closes |
| parallel fan-out | one superstep, N subagent branches | `Send` via `addFanOut`; join reads returned state |
| conditional edge | no event; observable as the next `step/start` | router reads state only |
| checkpoint `put` | at the boundary, after `step/end` | never mid-step |
| checkpoint `get` / resume | in-turn `InTurnCheckpointer` (kernel C5) | no cross-process mid-turn resume by design |
| human gate | `ask_user_question` tool call inside a step | never kernel `interrupt()`: it re-runs the node body (measured in the LangGraph spike) |
| replan | `withTopology` + one `user/message` banner at a boundary | plan version is model-visible and logged |
| run end | `step/end`, `turn/end` | terminal node routes through `agent/turn-stopping` |

Implementation: the kernel adapter calls `RunOptions.onBoundary` between supersteps
(`design/kernel.ts`); that callback is the *only* place the driver appends `step/end` +
`step/start`. Node bodies append what happens inside their step. This satisfies kernel
obligation A1 while keeping the log order identical to execution order.

### 2.2 What the driver reuses and what it replaces

Reused (must not be re-implemented): tool resolution and the guarded pipeline
(`ctx.tools.resolve/execute`), prompt assembly (`ctx.systemPrompt.assemble`), the
`agent/pre-step` waterfall (compaction, plan mode, instruction plugins), `prepareCall`,
the session append rules, `deriveMessages`, token meter, persistence handles, inbox,
`agent/turn-stopping`.

Replaced: *which* step runs next, *which* instruction the step carries, *which* tool
policy applies, and (optionally) *which model* the step uses.

`design/runtime.ts#STEP_PIPELINE_ORDER` is the literal order the step executor must
follow. A conformance test asserts it; a deviation is a bug, not a style choice.

### 2.3 Graph state

`LoopState` (`design/runtime.ts`) has only JSON values: task hash, plan id/version,
superstep, next node, status, facts, artifact *references* (path+hash, never bodies),
child session ids, a bounded journal, budgets and replan count. It is capped at 64 KiB
and validated with `assertJsonSafe` before every checkpoint write
(`design/graph-schema.ts`). The spike measured that `Date`→string and `Map`→`{}` across a
JSON round-trip, so the type system forbids them.

### 2.4 The stock-equivalent graph is the control arm

`explore` and stock sessions cannot coexist in one process (a single factory slot), so
A/B needs either two profiles or one driver that can emulate the old behavior. We do the
latter: template `t_stock` compiles to a single self-looping `agent-step` node with the
full tool set. Running the same driver in `plan: stock` mode gives an in-process control
arm with identical seam usage; `plan: explore` is the treatment. This removes the
"different process, different noise" objection from the benchmark.

## 3. Node executors

A node is one unit of work with exactly two legal executors. `design/graph-schema.ts`
validates the pairing (e.g. every parallel branch must be `subagent`).

### 3.1 `step` executor (default)

Contract:
- **Input**: state slice, node instruction, `toolAllow`, optional model route.
- **Effects**: one model request + its tool batch, logged as a normal step.
- **Prompt**: the graph-level guidance lives in one stable system-prompt section
  (graph persona/route rules). The **node instruction is appended as a `user/message`**
  (source `{kind:'graph-loop'}`, ~80–150 tokens ESTIMATE) immediately before the step's
  own user batch — append-only, so the cached prefix is not rewritten. This is the
  deliberate delta D03 and the main instruction-assembly cost of the design.
- **Tools**: the plan's `toolUniverse` is the visible set. Per-node `toolAllow` is soft
  by default: a `ctx.tools.guard` denies out-of-node calls with a model-facing reason
  (`Error: …`, one result, turn continues). No schema change, no cache invalidation.
- **Model**: `agent.model.select({provider, model, reasoningEffort})` before the step is
  prepared; records `model/selection` and a `request/header` change snapshot when it
  differs (conformance C11/D02).
- **Output**: deterministic post-condition validator → `NodeOutcome.facts/artifacts`.
  Validators read durable tool results; they never parse free-form model prose for
  routing, because prose classification would not be reconstructable on restore.

KV behavior: the prefix is stable across nodes of one plan (same system prompt, same tool
declarations). Per-node instruction messages append after the prefix. This is the main
improvement over the control-plane design, which had to rewrite the system prompt per
node.

### 3.2 `subagent` executor (parallel / isolation-heavy nodes)

Contract:
- **Input handoff**: JSON object serialized into one text block of the child prompt,
  ≤ 16 KiB (`GRAPH_STATE_LIMITS.maxHandoffInputBytes`), e.g.
  `{"area":"packages/core/tools","question":"…","files":["…"]}`.
- **Call**: `ctx.subagents.startActivation({provider, label, request:{parent, prompt,
  signal, agentPreset?, agentOptions?, outputSchema?, maxDepth?}, delivery:'caller'})`
  (`docs/subsystems/subagent.md`). Caller delivery means no parent settlement notice; the
  graph runtime awaits `result`.
- **Output**: `result.structured` validated against the node's object-rooted
  `outputSchema`; ≤ 8 KiB. The parent logs it as the synthetic delegation tool result, so
  the parent's model sees a compact result and the parent's log remains self-contained.
- **Durability**: `subagent/catalog` (and `subagent/descriptor` when the provider writes
  one) in the parent, full child session in the child. This is why subagent nodes are
  resume-friendly even without a checkpoint: the parent catalog is a known event type.
- **Failure**: `stopReason` `failed|cancelled|limit` → `NodeFailure{subagent-failed}`,
  retryable only if the node's `retry` allows and the child is re-runnable (fresh
  sessions are; continuable children may not be). A failed fan-out does not fail the run
  unless the join node requires all branches; the plan's `when` condition decides.
- **Idempotency**: subagent nodes are *not* idempotent (the child ran). A retry after an
  unknown outcome must be a new child with a "verify before redo" instruction, or a
  replan. `PlanNode.idempotency` records which is legal.

### 3.3 Parallel supersteps

A parallel node's branches are `subagent` nodes; the driver spawns them in one superstep
and joins through state reducers at the next. `maxActiveSubagents` defaults to `8` in
`ctx.subagents` (`packages/subagent/subagent/README.md#activation-capacity`), which is
the practical fan-out ceiling. Branch results join into `facts`/`artifacts`; artifacts
are references only. Contract: no two branches may write the same artifact without a
join validator (checked in `design/graph-schema.ts` warnings).

## 4. The registry graph

`design/graph-schema.ts` defines nodes (tool / skill / subagent-provider / preset /
agent-role / plugin / surface) and typed edges: `requires`, `produces`, `substitutes`,
`similar`, `conflicts`, `permission`, `budget`, plus plan-level `control`/`data`.

Built at plugin activation from live registries; kept live by
`tools/change` (unfiltered registry notification,
`docs/subsystems/tools.md:751`), `system-prompt/change`, `skills/change`, preset
revisions, and HMR plugin rows. Each snapshot carries `version`, `digest`, `sources`,
and explicit `warnings` for blind spots (dynamic MCP tools, conditional registrations,
PTC-vs-native conflicts).

The one thing DSH does **not** expose is capability semantics: artifact types, cost, risk,
preconditions. Those come from a versioned annotation layer
(`design/example-graph.yaml` is the shipped subset) merged with measured facts (schema
size from the catalog, failure rate from `tool/result`, latency from telemetry). The
annotation layer is data, reviewed like code, and can be overridden per deployment.

## 5. Similarity: the honest part

### 5.1 Why description-embedding cosine is not a router

Concrete DSH counterexamples (kept in `design/matching.ts#WHY_COSINE_IS_NOT_ENOUGH`):
- `read` / `read_image` / `read_mcp_resource`: near-identical descriptions, different
  artifact types and execution worlds.
- `bash` / `pwsh` / `run_code`: near-identical descriptions, but mutually exclusive by
  platform or executor; cosine cannot express exclusivity.
- `edit` / `write` / `str_replace_editor`: same artifact, different preconditions
  (read-before-edit, uniqueness).
- `grep` / `session_search`: both "search", different corpora.
- `subagent` / `workflow` / `ralph`: all orchestration, very different cost, parallelism
  and durability.
- Descriptions are generated docs (`docs/tool-catalog.md` header), so an embedding index
  is stale the moment a plugin changes; the router would silently drift.

Similarity is also the wrong objective: the matcher needs *applicability* (preconditions
satisfied) and *sequence viability* (produces→consumes), not pairwise resemblance.

### 5.2 The layered signal model

1. **Declared typed edges** (strongest): artifact `produces`/`requires`, `substitutes`,
   `conflicts`, `permission`. Curated, versioned, reviewable.
2. **Deterministic schema features**: parameter-name Jaccard, parameter type overlap,
   output artifact overlap, name/description token overlap (BM25-like). No model calls.
3. **Mined co-occurrence** from `ctx.sessionQuery` (see 5.3): sequencing affinity, not
   resemblance.
4. **Measured priors**: schema tokens, per-call tokens, failure rate, p50 latency,
   template success rate.
5. **Embeddings**: tiebreaker only, weight ≤ 0.05, never in the v1 scoring path; used
   offline to *propose* `substitutes`/`similar` edges for human review.

### 5.3 Co-occurrence mining

Source: `ctx.sessionQuery.filterEvents(sessionId, {eventType: ['tool/call']})` over
historical sessions (`packages/session-query/.../README.md`). Only successful turns
contribute (a failed turn co-occurs for the wrong reason).

```
P(a,b) = pairs(a,b) / totalCalls
PMI    = ln( P(a,b) / (P(a)P(b)) )
NPMI   = PMI / -ln P(a,b)                    ∈ [-1, 1]
w(a,b) = max(0, NPMI) · n/(n + k)            Bayesian shrinkage, k = 10, n = observations
handoff(a,b) = count(b immediately after a) / count(a)
```

Edges below `minObservations = 20` are dropped. The table is versioned and rebuilt
offline (nightly or on registry change), never on the request path. Complexity
`O(S + Σ_turns |turn|²)`; turns are small (median 3–8 calls), so this is cheap.

### 5.4 Calibration and fallback

Weights are data (`design/example-graph.yaml#weights`), not code. Offline calibration
(`design/matching.ts#calibrate`): coordinate ascent on the weight simplex maximizing
top-1 template accuracy, with fallback precision/recall reported alongside; grid search
when samples < 200. Labels come from the bench's task set and from historical successful
runs (template used ∧ turn succeeded). Metrics: top-1 accuracy, fallback rate, cost
delta, success delta. Recalibrate on graph-digest change or success-rate drift.

Safety valve: if the best score is below `absMin` (0.55) or the margin over the runner-up
is below `marginMin` (0.08), the match returns the conservative `t_default` plan and
records `fallbackReason`. A failed run of the same fingerprint forces the fallback on the
next attempt (`previousFailure`). Every decision is explainable: `MatchResult.explain`
lists why each template was skipped and how each slot was bound; `graph_status` surfaces
it.

## 6. The match

### 6.1 Task fingerprint (deterministic, rule-based)

`text` → normalized (NFKC, lowercase, collapsed whitespace) → intent class from a small
lexicon with priority ties (`test-failure` beats `bug-fix` beats `code-change`), artifact
types from path extensions and attachments, risk band from mutating verbs, context
bucket from `ctx.tokenMeter`, surface, explicit tool-name hints, workspace facts (git,
package.json, tests, language). No model call, no clock, no randomness; arrays sorted;
`hash16` is FNV-1a over canonical JSON. Same input ⇒ same fingerprint ⇒ same route.

### 6.2 Hard filter, then beam search

1. **Admissible templates**: preset offers every tool in the template's universe; intent
   matches; mutating/parallel flags compatible; every tool is present and not
   conditional/dynamic.
2. **Slot instantiation**: each slot has `choose: [tool…]` and a preference
   (`artifactMatch|intentMatch|successRate|cost`). Beam search (width 8, ≤6 candidates per
   slot) explores bindings; ties break on the sorted binding tuple, never map order.
3. **Score** (all terms normalized to [0,1]):

```
score =  w_i·intentMatch + w_a·artifactMatch + w_t·toolAffinity + w_h·historySuccess
       − w_c·costPenalty − w_r·riskPenalty
```

with `intentMatch∈{0,1}`, `artifactMatch` = coverage of required artifacts by the plan's
productions, `toolAffinity` = mean mined/declared edge weight along slot order,
`historySuccess` = Laplace-smoothed template success, `costPenalty` = estimated plan
tokens / 250k, `riskPenalty` = template risk. Defaults sum to 1.0
(`0.26 + 0.30 + 0.16 + 0.12 + 0.10 + 0.06`).

Complexity: `O(T·b·S·C)` scoring calls, each `O(E)`; with the shipped limits (≤24
templates, b=8, S≤6, C≤6, E≤30) that is < 100k primitive ops — sub-millisecond on Node
26. Determinism and caching: `RouteCache` keyed by
`(taskHash, graphDigest, weightsVersion, presetId)`, 256 entries.

### 6.3 Worked trace (task → match → 3 nodes → replan)

Task: *"The auth test fails after the refactor — fix it and prove it."*

Fingerprint: `intent=test-failure`, `artifactsIn=[file.text]`, `mutating=true`,
`risk=medium`, `contextBucket=1`, surface `cli`, hints `[]`. Candidates (design YAML):
`t_code_edit_test` 0.82, `t_code_investigate` 0.61, `t_data_analysis` 0.44 →
**selected `p_code_edit_test@3`**, confidence 0.82, margin 0.21.

| # | Node (executor) | What happens | Durable events | Est. tokens |

| — | plan start | banner + cold hard gate to the 8-tool universe (3,454→1,203 schema tokens) | `turn/start`, `step/start`, `user/message`(banner ≈40) | 40 |

(~700) and two banners (~80). The bench owns the real numbers; this trace exists to show
the shape and the event mapping, not to claim a percentage.

## 7. Template library and the `explore` preset duality

The **same plan document** is used two ways:
- **as the compiled loop graph**: nodes/branches/edges are what the kernel runs;
- **as the preset's template library**: `preset = tool universe + persona`, and the
  template is the path a task takes through that universe. The preset's tool set is the
  union of its templates' universes; the plan narrows it at cold boundaries and softly
  per node.

Shipped templates (`design/example-graph.yaml`):

| Template | Task class | Universe | Shape |
|---|---|---|---|
| `t_stock` | A/B control | all | single self-loop step |
| `t_code_investigate` | code question/review | glob/grep/read/bash/todo | 2 slots, read-only |
| `t_code_edit_test` | change/bug-fix/test-failure | read/edit/write/glob/grep/bash/todo/present | discover→patch→verify→report, bounded loop |
| `t_research` | research/fact-finding | web_search/web_fetch/read/write/present | search→read→synthesize |
| `t_doc_generate` | document | skill/read/write/present/bash | load skill→draft→deliver |
| `t_data_analysis` | data analysis | read/bash/write/present/todo | inspect→compute→report |
| `t_multi_agent_fanout` | wide research / multi-area review | subagent/read/grep/glob/write/present | parallel subagents→join→report |

Each carries `appliesTo` predicates, `risk`, `gatePolicy`, tool universe and a superstep
budget. Deployment templates are YAML validated against `TASK_PLAN_JSON_SCHEMA`
(`design/graph-schema.ts`); the loader rejects a template whose tools are not in the
preset.

## 8. Dynamic add/remove and replan

**Replan = recompile + resume.** `applyMutations` (`design/replan.ts`) transforms the
plan document (insert gate, remove node, swap binding, relax tools, escalate model, force
terminal), recompiles via `kernel.withTopology`, and resumes the thread with
`updateState` at the current boundary. Invariants are checked before the swap and again
by the kernel's JSON validator.

Triggers (`ReplanTrigger`): tool failure (twice), validation failure, no progress (same
tool 3× via the repeat detector), budget exhaustion, user steer that changes intent,
subagent failure, graph error.

Limits and rollback: `maxReplans` per plan (default 3), one mutation set per boundary,
the previous plan version retained; a failed recompile or a second failure on the same
trigger falls back to `t_default`; the budget ceiling aborts with a report. Every replan
appends exactly one banner (≤ 40 tokens) so the log explains the topology to the model
and to a human reader.

Tool gating policy (see `design/measurements.md` for the numbers): hard gating only at
cold boundaries by default, because changing declarations invalidates the prefix from the
first changed schema token and DSH's own base bundle keeps the catalog constant across
modes "for request-cache stability" (`packages/bundle/base/cordis.patch.yml:340`). Soft
gating (guard denial) is per node and cache-free.

## 9. Durable state: resume, fork, compaction, idempotency

**Constraints.** An out-of-tree plugin cannot extend `SessionEventMap` (compile-time,
repo-checked) and must not call `appendPluginRecord` (documented policy, external plugins
"must not", `packages/core/session/README.md:72`). So the graph loop emits only known
event types, and graph state is not a session event.

**What survives what:**

| Fact | Durable form | Resume | Fork | Compaction |
|---|---|---|---|---|
| user input, assistant messages, tool calls/results | session events | replayed | prefix copied | surface shadowed, raw log kept |
| plan identity/version | `user/message` banner (D07) | retained | copied | may be shadowed → re-inject after `compaction/end` |
| node progress | `step/end`, `tool/call|result`, `subagent/catalog` | fold → state | fold → state | unaffected |
| child sessions | `subagent/catalog` + child logs | discoverable | copied prefix; children are separate sessions | unaffected |
| in-flight graph channels | in-turn `InTurnCheckpointer` (JSON) | not needed | not needed | not needed |

Kernel C5 is the load-bearing decision: DSH closes an interrupted turn with synthetic
closers on restore (`packages/core/session/src/repair.ts`), so a graph run never resumes
across a restart. The checkpointer exists for in-turn time-travel (replan, debugging) and
for the property test that folds the log and compares it with the checkpoint state. That
test is the real assurance: **the log must be sufficient to recompute what the graph
believed**, because routing decisions are deterministic functions of logged facts.

Idempotency: nodes are marked `idempotent | verify-before-retry | manual`. Mutating nodes
require a post-condition validator (`validateTaskPlan` warns otherwise); a retry after an
unknown outcome must verify first, mirroring DSH's own recovery wording for
`TOOL_OUTCOME_UNKNOWN` (`packages/core/session/README.md#tool-result-recovery-and-fork-results`).
Subagent nodes are never idempotent.

Fork: the child copies the log prefix, so a deterministic fold yields the same plan and
the same completed-node set. Nothing about the graph needs copying outside the log —
which is exactly why the design refuses to put durable graph state in a sidecar store.

## 10. Seams: every element mapped, and what would need a source change

| Design element | DSH API / seam | Source change? |
|---|---|---|
| registry snapshot (tools) | `ctx.tools.schemas()`, `tools/change` | no |
| registry snapshot (skills/presets/subagents) | `ctx.skills`, `agent-preset-registry`, `ctx.subagents` | no |
| capability annotations | plugin-owned YAML data | no |
| factory replacement | profile patch disabling `agent-loop` row + `ctx.agents.setFactory` | no (composition) |
| step tool policy | `ctx.tools.resolve`, `ctx.tools.restrict`, `ctx.tools.guard` | no |

## 11. Conformance (feeds the test suite)

`design/conformance.ts` enumerates 16 preserved obligations and 8 deliberate deltas. The
headline:

**Preserve byte-for-byte:** event order/enclosure (C01), `request/header` snapshot and
inheritance (C02), `request/context` on route change (C03), system-prompt admission (C04),
tool-schema projection and order (C05), tool result/error rendering (C06),
`developer/message` on tool changes (C07), inbox/injection semantics (C08), cancellation
and undispatched-call results (C09), failed-step recovery (C10), per-step durable model
selection (C11), `agent/pre-step` (C12), compaction brackets (C13), persistence write
handles and interrupted-turn closers (C14), `agent/turn-stopping` (C15), live UI events
(C16).

**Deliberate deltas:** graph-driven step selection (D01), per-node model (D02), node
instruction as a user message (D03), synthetic `graph:delegate` calls (D04), cold-gated
tool universe (D05), early terminal turns (D06), plan banner (D07), graph state not in
the log (D08).

**Test plan.** The decisive test is a differential replay: the same `llm-replay` fixture
(`packages/test-support/llm-replay/README.md` — keyless replay of a recorded session)
under the stock profile and the `explore` profile, then diff the durable event streams
after removing `ALLOWED_DELTA_TYPES` and normalizing volatile envelopes. Fixtures:
read-only question, failing-test fix, cancelled turn, compaction mid-run, ask-user gate,
subagent fan-out. Plus: a property test folding the log into `LoopState` and comparing
with the checkpoint; a crash/restore test (closers, no duplicate step); a fork test;
a budget test (`GraphRecursionError` → step-budget stop, not a crash).

## 12. Top risks

1. **Conformance surface (highest).** Replacing the driver means re-implementing ~16
   obligations, some subtle (prompt admission, header inheritance, recovery results).
   Mitigation: reuse the pipeline order, make events the contract, ship behind a profile,
   gate on the replay diff, and keep the stock profile as the fallback.
2. **A wrong match costs more than no graph.** Mitigation: confidence gate, fallback
   template, `previousFailure` downgrade, per-template success tracking, and the
   `t_stock` control arm in the same process.
3. **Cache economics.** Per-turn hard gating is a net loss at realistic prefix sizes
   (~120-step break-even). Mitigation: cold-only default, soft per-node gating, measure
   `cacheReadTokens` not just prompt tokens.
4. **LangGraph drift / kernel coupling.** Measured version: 1.7.0 on Node 26; the kernel
   file isolates the dependency behind structural ports and records the upgrade checklist.
5. **Subagent cost and UI clutter.** Fan-out multiplies sessions and latency; cap with
   `maxActiveSubagents` and per-template budgets, and prefer sequential subagents unless
   the task is genuinely parallel.

## 13. Non-goals (v1)

- Learned end-to-end router (no trained policy; calibration only tunes ≤6 numeric
  weights offline).
- Parallel *steps* in one session (DSH runs one step at a time; parallel means children).
- Unbounded graph loops; every cycle is a bounded `map` node.
- Custom session events or plugin records (external-plugin policy).
- Mid-turn resume across process restarts (kernel C5; DSH closes turns on restore).
- Runtime mutation of a compiled graph without recompilation.
- An LLM judge inside the matching path (deterministic matcher only).
- Migrating `ralph`, `workflow`, or `agentTeams` onto the graph in v1.

## 14. Open decisions for the Lead

1. **`explore` packaging.** Profile + bundle (`dsh explore`) is the only clean option
   given the single factory slot. Per-session mode would need a new session event
   (source change) or preset-only gating. *Recommend profile, two processes for A/B.*
2. **Delegation step semantics (`CONFORMANCE_DECISIONS` CD-3).** A subagent node currently logs a synthetic
   `graph:delegate` tool call inside a no-request step. Alternative: no step at all. The
   first is more uniform but adds a tool call the model did not emit; the second needs
   step-enclosure exceptions. *Recommend the synthetic call, validated against the Web UI
   and `ToolCallRecovery`.*
3. **Default gate policy.** `cold` vs `turn` — bench-driven; keep `cold` until the
   token-economist shows a per-turn win.
4. **Who owns the template library.** Ship the six templates in the bundle, allow
   profile YAML overrides? *Recommend ship + override.*
5. **Per-node model selection.** More `model/selection` events and cache misses; restrict
   escalation to verify/repair nodes? *Recommend yes, and measure.*
6. **`graph_status` / `graph_explain` as model-facing tools.** Useful for debugging and
   for user trust; costs schema tokens in every request. *Recommend an operator UI +
   `/graph` command, not a model tool.*
7. **Whether the plan banner should be a user message or a system section.** User message
   is append-only (cache-friendly) but visible in the transcript; system section is
   cleaner but rewrites the prefix. *Recommend user message, as designed.*
8. **Kill criteria.** Recommend: replay-diff diverges outside deltas, or success drops
   >3 pp, or cache-adjusted billed input regresses >5 % on the bench → ship `stock` mode
   only and keep the registry/matcher as an observe-only feature.
