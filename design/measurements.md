Scope: the numbers the graph-loop design relies on. Everything here is reproducible
from the read-only DSH checkout; no DSH source was modified.

`docs/tool-catalog.md` is generated by booting every shipped tool plugin and reading
`ctx.tools.schemas()` (`gen-tool-catalog.ts` header), so these are the exact JSON
Schema strings the model receives. The `chars / 4` heuristic is the one the repo's own
token meter uses for undeclared routes; the token-meter README warns JSON schemas
"underprice badly at four characters per token", so treat the numbers as a **lower
bound**.

## What gating can and cannot save

Gating a plan down to its tool universe removes `B - G` tokens of declarations
(base 3,454 -> coding 1,203 = **2,251 saved** in the best realistic case). But
`packages/core/tools/README.md` is explicit: a changed visible definition
"may invalidate reuse from the first changed schema token", and the DSH base bundle
deliberately keeps the tool catalog constant across plan mode "for request-cache
stability" (`packages/bundle/base/cordis.patch.yml`, plan-mode section). So:

```
save/step     = (B - G) * c                  c = cache-read price / input price
miss cost     =  P * (1 - c)                 P = prefix tokens (system + tools + history)
break-even N* =  ceil( P * (1 - c) / ((B - G) * c) )
```

With `c = 0.1` (DeepSeek cache-hit pricing, **ESTIMATE** — verify with the
token-economist) and `P = 30,000`:

`N* = ceil(30,000 × 0.9 / (2,251 × 0.1)) = ceil(27,000 / 225.1) = 120 steps`

A 120-step amortization inside one conversation means **per-turn hard gating almost
never pays**. Hence `gatePolicy: cold` is the default in `design/runtime.ts`: gate at
session start, after compaction, on fork, or on a model switch (the prefix is cold
anyway), and keep the declaration set stable inside a run. `design/replan.ts#decideHardGate`
implements this inequality with live `ctx.tokenMeter` inputs rather than a constant.

## Graph-loop cost envelope (ESTIMATE)

Assumptions: base composition 3,454 schema tokens; system prompt + persona not
measured here (the token-economist's bench owns it); history grows by ~600–900 tokens
per step (assistant message + tool results).

| Component | Stock loop, 12-step task | Graph loop, same task |
|---|---|---|
| Tool schemas per request | 3,454 | 1,203 (plan universe, cold-gated) |
| Node instruction (append-only user/message) | 0 | ~100 × 6 nodes ≈ 600 |
| Plan banner | 0 | ~40 × 2 ≈ 80 |
| Explore subagent (fresh context) | 0 | 1 child × (3,454 + task + ~4k work) ≈ 8k one-shot, parent sees ~250-token result |
| Parent history replay | 12 steps × growing history | 6 steps × smaller history |

Net effect (ESTIMATE, to be measured by the bench): a **20–35 % reduction in billed
input** on multi-file investigate/edit/verify tasks, driven mostly by the fresh
subagent context for discovery, **not** by per-node schema gating. On a single-turn,
3-step task the graph loop is within noise and may lose to the plan banner overhead.

## Graph-state size (MEASURED by construction)

`GraphState` in `design/graph-schema.ts` is JSON-only and reference-only:
artifacts store path + hash, never file bodies. `GRAPH_STATE_LIMITS.maxCheckpointBytes`
is 64 KiB; the journal is capped at 64 entries. A typical plan (8 nodes, 12 facts,
5 artifacts) serializes to ≈ 3–6 KiB, well inside the kernel's in-turn memory
checkpointer and inside a JSON round-trip (the LangGraph spike measured that `Date`
becomes a string and `Map` becomes `{}`, which is exactly why the schema forbids them).

## Subagent handoff sizes

`maxInputBytes` 16 KiB / `maxOutputBytes` 8 KiB (`GRAPH_STATE_LIMITS`). Rationale: the
input is repeated in the child prompt and the output is injected back into the parent
as one user message, so a 16/8 KiB pair bounds the parent cost at roughly 4k + 2k
tokens even when a child misbehaves. The child's own transcript is not bounded by this
and is paid in its own session.
